# Calling behavior research and scope

Reference: Vapi's **official public documentation** in [VapiAI/docs](https://github.com/VapiAI/docs), inspected at commit `745569ce06e7f4cb1e812770a00cc3005e89e01c`. The docs website was denied by this environment's network policy; the repository was retrieved through the configured GitHub proxy. These documents describe public behavior, not Vapi's private service architecture. This project is an independent implementation, not Vapi's source code or a drop-in API clone.

Both description and phrase routing work. State persists for restart recovery. See [implementation and limits](warm-transfer.md). |
| [Custom functions](https://docs.vapi.ai/tools/custom-tools)                                              | Reusable functions have name, description, JSON Schema, server URL, timeout; runtime webhook is `message.type = tool-calls`, returning `results` correlated by `toolCallId`.                                                | Separate registry/executor. Synchronous functions only; not the complete Vapi function API.                                                                                                                                                                      |
| [DTMF/IVR](https://docs.vapi.ai/ivr-navigation)                                                          | Wait for complete menu; avoid speech over tones; `w` = 0.5s, `W` = 1s.                                                                                                                                                      | DTMF tool generates G.711 mu-law tone pairs over the media channel and waits for playback. In-band tone compatibility needs real IVR testing.                                                                                                                                                                             |
| [Voicemail](https://docs.vapi.ai/calls/voicemail-detection)                                              | Detection and message playback are separate; wait for mailbox greeting/beep to avoid clipping. Multiple detectors can conflict.                                                                                             | Twilio synchronous AMD only. `Enable` for hangup, `DetectMessageEnd` for leaving a message. End-of-greeting result starts an ElevenLabs message; acknowledged playback precedes hangup. Scheduling/batch campaigns are not implemented in this increment.                                                                                                                                                                                                        |

## Boundaries

Implemented scope is the requested Twilio + Deepgram + ElevenLabs + OpenAI pipeline and the three tool types. Vapi has much more than this scope. No claim of full Vapi feature, latency, reliability, or API parity is made.

Still separate work: general-purpose conference controls, recordings, campaign scheduling and retries, full event subscriptions, provider failover, assistant publishing/version history, multi-tenant deployment, and production load/latency testing. Warm-transfer recipients use the originating assistant's provider settings; separate per-destination assistants and autonomous IVR navigation during consultation are not implemented. Self-hosted Google Meet participation and HeyGen LiveAvatar LITE rendering now have separate transport adapters; see [meeting setup and validation boundaries](google-meet.md). Compliance workflows were deferred as requested.

Provider credentials and outbound network permissions were absent during development. Automated tests use explicitly isolated provider doubles and Twilio-format messages. Live voice quality, device screening, voicemail timing, and real transfer/IVR interoperability require controlled phone calls after configuration.
